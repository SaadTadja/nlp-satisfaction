Stage detail

What each stage actually contains

01

Data complete

Collect / Store

tblard/allocine — 200,000 real French reviews, 160k/20k/20k. Audited before use: five checks, each settling one downstream decision. The corpus is never copied or mutated; every split is an int64 index array over one immutable source.

  • 49.6/50.4 balance → no weighting
  • 46 cross-split dupes
  • 6 label conflicts
  • 625 KB total index storage
02

Processing complete

Clean / Transform

One normalize(), versioned and imported by training, evaluation and serving alike — NFKC, strip markup and URLs, collapse whitespace. It deliberately preserves case, punctuation, accents and emoji, because the audit showed 96.3% of reviews carry uppercase and “NUL” is not “nul”. Features are TF-IDF word 1–2 grams unioned with char_wb 3–5 grams.

  • 288 max_length (p90)
  • 9.8% truncated
  • v1 normalize version
03

Model complete

ML — classifier, calibration, estimator

Three stacked components, not one. A LogisticRegression classifier; a temperature that makes its probabilities trustworthy; an abstention band over those probabilities; and the prevalence correction that turns per-comment output into a population estimate. The encoder is a swappable backend — the transformer path is written and awaits GPU training.

  • T = 0.6268
  • ECE 0.0545 → 0.0077
  • band [0.257, 0.709]
  • 8.5 MB artifact
04

Evaluation complete

Metrics / Tests

Two independent things are evaluated, because the system makes two different kinds of claim: per-comment classification, and population-level estimation. The test split was held back through every phase and read exactly once, with all parameters frozen.

  • 0.9195 macro-F1 forced
  • 0.9611 confident only
  • 10.5× ACC over naive counting
  • 9/9 CI coverage
  • 57 unit tests, no GPU
05

Application runs locally

UI / App

Gradio, two tabs. The primary one takes a CSV of feedback and returns a report — corrected satisfaction rate, confidence interval, neutral count, per-topic breakdown — not a label. The second takes a single comment for inspection. Verified end to end on 300 held-out reviews skewed to a known 30.0% true rate; it returned 32% [25–38%].

  • 5,000 row cap
  • guards empty · non-French · truncation
  • no API, no DB, no auth

Deployment not done

Cloud / Server

07

Monitoring out of scope

Logs / Drift

Deliberately absent for v1. The model is a static artifact pinned by commit, there is no retraining loop, no persistent state, and no production traffic to observe. Building a monitoring stack for a demo would be the kind of over-engineering the architecture elsewhere avoids on purpose.

That said, the design already emits the one signal that would matter most — see below.

Stage 7, if it existed

The drift signal this architecture gives away for free

The abstention band exists to decline guessing on ambiguous text. It also happens to be a usable distribution monitor, at no extra cost.

On Allociné the band catches a stable share of inputs: 9.6% on test, 10% by construction on validation. If that rate climbed to 25% on live traffic, it would mean incoming text is landing near the decision boundary far more often than the corpus the model was fitted to — which is what domain shift looks like from the inside.

One number, already computed on every request, already logged by the batch tab: the share of comments the model declined to judge.

A real stage 7 would track three things, in this order of value:

  • Abstention rate — the cheap drift proxy above. Alert on a sustained move away from ~10%.
  • Input length and language distribution — catches the obvious failure of someone pasting English or a different text genre.
  • Periodic re-labelling of a small sample — the only one that actually re-measures TPR/FPR, and the only one that can tell you the correction has gone stale.
Why the third one matters most

The aggregate estimate divides by (TPR − FPR), and those constants were measured on film reviews. On a different domain they are wrong by an unknown amount — and the confidence interval does not know it, because it propagates holdout uncertainty and zero domain shift.

So the app would keep printing “32% [25–38%]” with full apparent rigour while the true rate sat outside that range. A narrow dishonest interval is worse than no interval. Re-labelling a sample periodically is the only thing that detects it.

Honest summary

Where this actually stands

Five stages complete, evaluated once on held-out data, with a working application. Two stages open: one needs an account, one was decided against.

The gap that matters is in none of the seven boxes, because it cuts across them: the entire pipeline is built and measured on film reviews, and it is presented as a client-satisfaction tool. Closing that needs 150–300 hand-labelled French product and service comments — which cannot be auto-generated, since labelling them with a model would make the agreement figure measure agreement with the system under test.
