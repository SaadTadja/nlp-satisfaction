Satisfaction Pipeline Architecture

An offline batch pipeline that produces one artifact, and a stateless demo that serves it. The whole design answers a single question: how do you guarantee that the thing you measured and the thing you serve are the same thing?

The driver

Two questions, measured two different ways

Almost every sentiment system measures per-comment accuracy and reports it as though it answered the business question. It doesn't — and the gap between the two is what shapes this architecture.

Model questionProduct question
asksIs this review positive?What share of clients are satisfied?
unitOne commentA population of comments
metricAccuracy, macro-F1Estimated prevalence + interval
fails whenIt misclassifiesIts errors are asymmetric

A classifier at 96% accuracy whose errors skew one way reports “14% satisfied” for a population that is truly 10% satisfied. Accuracy never surfaces that. It needs a different estimator, layered on top.

So the system has two stacked components with separate acceptance criteria: a classifier, and an estimator built on it. Everything below exists to keep those two honest about each other.

Four rules the code enforces for you

Each of these is a failure that produces no error message — the system keeps running and quietly stops being true. That is exactly the class of bug worth spending architecture on.

Guard

One prediction path

The notebooks and app.py import the same predict(). No notebook may reimplement a stage — writing softmax inline means the contract is already broken.

Guard

Normalisation drift alarm

The config carries normalize_version. If it diverges from the code, loading raises instead of serving text that differs from what was evaluated.

Guard

No aggregation before measurement

require_aggregation=False lets notebook 06 predict in order to measure the rates, but the resulting config refuses to emit a satisfaction figure.

Guard

Missing fields name their owner

An unfilled value reports temperature: produced by notebooks/04_calibration.ipynb — the pipeline documents its own ordering instead of raising a KeyError.

Modules

Four files, one responsibility each

ModuleOwnsDepends on
normalize.pyText canonicalisation, versioned. Preserves case, punctuation and emoji — all carry sentiment signal in reviews.—
estimate.pyThe ACC correction, confusion rates, bootstrap intervals over both uncertainty sources, prevalence resampling.numpy
aspects.pySentence splitting, lexicon matching, corpus-derived lexicon persistence.—
predict.pyConfig loading and validation, the two backends, the pipeline, the aggregate entry point.the other three

The first three are pure Python and numpy. Only predict.py can reach torch, and only lazily inside TransformerBackend.__init__ — which is why the whole suite runs in four seconds on a laptop with no deep-learning stack installed.

Scope

Deliberately absent

There is no persistent state, no concurrency problem, and no scaling requirement. Each of the following is defensible on a larger system and is pure overhead here.

  • databaseNothing to persist. Every request is independent.
  • authA public demo with no user-specific data.
  • request queueGradio's default handles demo traffic; the batch cap is 5,000 rows.
  • retraining loopThe model is a static artifact, versioned by commit.
  • API versioningGradio's generated endpoint is incidental, not a product surface.
  • containersSpaces builds the image; a Dockerfile would be maintained for nobody.

If any of these were needed later, predict() is already the seam to build them against.

Numbers on this page are measured, not projected: macro-F1 and artifact size from 02_tfidf_model, temperature and thresholds from 04_calibration, error rates from 06_aggregate. The classifier is a bag-of-ngrams model — the transformer backend is written but untrained.
